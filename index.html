Webpack 빌드 최적화: 라우터 코드 스플리팅 개선

Vue 라우터 lazy-load의 변수 기반 동적 import가 Webpack context 모듈을 만들어 폴더 전체를 스캔하고 파싱하던 구조를, 정적 경로와 고정 청크명으로 바꿔 풀빌드 시간을 5분대에서 1분대로 줄인 작업. 이 개선으로 2025년 상반기 우수직원에 선정됐습니다.

Background / Problem
  • 라우터 lazy-load에서 경로와 청크명을 변수로 구성해, Webpack이 context 모듈을 생성하고 해당 폴더의 모든 후보 파일을 스캔하고 파싱
  • 풀빌드에 약 5분이 소요되고, 청크 경계와 이름이 자주 바뀌어 캐시 적중률이 낮음
  • 폐쇄망이라 빌드 인프라 증설이나 신규 번들러 도입으로 우회하기 어려운 조건
Solution / Process
  • 변수 경로 동적 import를 정적 파일 경로로, 변수가 섞인 청크명을 고정 webpackChunkName으로 통일해 정적 분석이 가능하도록 변경
  • 라우트별 독립 청크 그래프를 안정화해 모듈 스캔과 파싱량, 해시 변동을 최소화하고 캐시 적중률 개선
  • 동적 페이지가 필요한 경우 화이트리스트 매핑 객체로 한정된 집합만 로드하도록 제한
Result
  • 풀빌드 시간 약 80% 단축 (5분대에서 1분대로)
  • 절대값보다 누적 효과가 큰 개선. Vue 개발자 2명이 하루 5회 이상 테스트 빌드를 돌리는 환경이라, 하루 약 40분, 월 20영업일 기준 약 13시간의 대기 시간이 사라졌습니다
  • 정적 분석이 가능해져 변경된 라우트만 다시 빌드되고, 해시가 안정되어 재빌드 시간도 함께 감소
  • 배운 점: 번들러의 동작 원리(context 모듈, 정적 분석)를 이해하고 원인을 제거하면, 도구를 바꾸지 않고도 큰 개선이 가능하다는 것

스마트뱅킹 웹 접근성(KWCAG) 개선

외부 심사기관의 접근성 진단 결과를 받아, 스크린리더와 키보드만 쓰는 고객도 금융 거래를 끝까지 완주할 수 있도록 스마트뱅킹 WebView 화면과 공통 컴포넌트를 개선한 작업. 2025년에 이어 2026년 심사 대응도 7월에 완료했습니다.

Background / Problem
  • 진단은 외부 심사기관이 수행하고, 저는 지적 사항을 해석해 실제 코드 개선을 담당
  • 운영 중인 금융 화면이라 CSS와 기존 동작, API 계약을 건드리지 않으면서 마크업만으로 해결해야 하는 제약
  • 지적된 화면만 그때그때 고치면 신규 화면에서 같은 유형이 반복되는 구조
Solution / Process
  • 지적 사항을 유형별로 묶어 거래 완주를 막는 항목부터 순차 개선
  • Vue에서 :aria-pressed에 불리언 false를 바인딩하면 속성 자체가 DOM에서 제거되어 토글 상태가 읽히지 않는 문제를, 문자열 바인딩으로 전환해 해결. 의미상 맞지 않는 위치에 붙어 있던 속성도 함께 정리
  • 전체 화면 모달에 dialog 역할과 포커스 트랩 패턴을 적용해, 스크린리더 포커스가 뒤쪽 콘텐츠로 빠져나가지 않도록 조정
  • CSS 가상요소로 그려진 장식 아이콘은 대체 텍스트를 줄 수 없어, 기존 off-screen 숨김 클래스를 활용해 의미만 읽히게 처리
  • 반복되는 위반은 화면 단위가 아니라 공통 컴포넌트 레벨에서 수정해 재발을 차단
Result
  • 2026년 정보통신 접근성 인증 갱신심사 통과 (2025년 1차에 이은 2년 연속 대응)
  • iOS VoiceOver, Android TalkBack 환경에서 주요 거래 흐름을 실제로 완주하며 검증
  • 개선 기준을 정리해 화면 개발 시점부터 접근성이 적용되도록 팀에 공유
  • 배운 점: 접근성은 나중에 덧붙이는 기능이 아니라 마크업 품질의 결과이고, 프레임워크의 속성 바인딩 규칙 같은 세부가 결과를 좌우한다는 것

공공마이데이터 연동 및 전자서명 통합 인증

공공마이데이터를 수신, 여신 상품 가입 흐름에 연동하고, 공동, 금융, 간편 인증서 3종 경로를 하나의 인증 흐름으로 묶어 고객 편의성과 검증 신뢰도를 함께 확보한 프로젝트.

Background / Problem
  • 인증서 종류(공동, 금융, 간편)마다 서명과 검증 경로가 달라 화면과 로직이 분기되고 유지보수 비용이 누적
  • 상품 가입에 필요한 공공기관 서류를 고객이 직접 준비해 제출해야 해, 가입 흐름 중간에 이탈이 발생하는 구조
  • 전자서명 결과의 신뢰 검증을 클라이언트에만 맡길 수 없는 금융 보안 요구
Solution / Process
  • 3종 인증서 경로를 공통 인터페이스로 추상화해 화면에서는 하나의 흐름으로 다루도록 정리
  • 전자서명(PKCS7) 결과를 백엔드에서 다시 검증하는 서버 사이드 라운드트립 구조로 구성해, 최종 신뢰 앵커를 서버에 둠
  • 인증서 SDK가 동일한 서명 데이터로 콜백을 두 번 발화해 재전송 방지 로직에 걸리는 문제를, 프론트에서 마지막 처리 데이터를 비교하는 중복 처리 가드로 해결
  • 배포 전 점검 항목으로 토큰의 저장 범위와 로그 노출 정책을 정의하고, 사용자 식별 요소를 포함한 저장 키 구조를 적용
  • 공공마이데이터로 확보한 정보를 상품 가입 페이지에 연동해 고객이 직접 입력하고 제출하던 단계를 축소
Result
  • 분기되어 있던 3종 인증서 경로를 단일 흐름으로 통합해 화면과 유지보수 복잡도 감소
  • 공공마이데이터 거래 4종 연동을 운영 배포까지 완료
  • 전자서명 검증의 최종 판단을 서버에 두는 구조로 정리
  • 배운 점: 인증 도메인에서는 편의성과 검증 신뢰를 함께 설계해야 실질적 개선이 된다는 것. 편의만 높이면 검증이 얇아지고, 검증만 세우면 고객이 이탈합니다

Background / Problem
  • 기존 인증 방식이 실물 신분증 하나로 제한되어 고객 불편이 있었음

Solution / Process

  • iOS와 Android에서 서로 다르게 동작하는 네이티브 브리지의 콜백 시점과 데이터 규격 차이를 각 OS 담당자와 맞춰 하나의 웹 인터페이스로 통합

Result
  • 앱 심사 없이 즉시 대응할 수 있는 운영 배포 환경 확보
  • 네이티브 2명의 공수 없이 웹 개발자 1명으로 이후 운영 개발이 가능한 구조
  • 인증 흐름을 웹으로 통일해 채널 간 유지보수 지점을 줄임
  • 배운 점: 구현 방식 선택은 기능 난이도가 아니라 이후 운영 비용으로 판단해야 설득이 된다는 것

요청받은 과제가 아니라, 운영을 지원하며 발견한 현업의 반복 업무를 하나씩 기능으로 바꿔 나가는 작업. 공지와 팝업의 채널 공통 등록에서 시작해 MAU/DAU 조회, 이미지 직접 삽입까지 이어지고 있습니다.

Background / Problem
  • 공지사항과 팝업을 채널마다 각각 등록해야 해, 같은 내용을 반복 입력하는 구조
  • 이용 지표 확인이나 이미지 교체처럼 자주 발생하는 요청이 매번 개발자 작업으로 넘어오던 상황
  • 내부 데이터 접근 통제가 강화되면서, 기존에 직접 조회로 처리하던 운영 업무를 어드민 기능으로 옮길 필요가 커짐
Solution / Process
  • 채널별로 분리돼 있던 등록 방식을 분석해, 한 번 작성하면 전 채널에 반영되는 공통 구조로 재설계하고 채널 분기로 모바일웹, 인터넷뱅킹, 앱 화면에 각각 맞게 렌더링
  • MAU/DAU 조회 기능을 추가해, 현업이 개발자를 거치지 않고 직접 이용 지표를 확인하도록 변경
  • 팝업 이미지 직접 삽입 기능을 추가. 이미지 저장소와 채널 조회 API를 분리하고, 접속 도메인으로 환경을 판별해 개발과 운영에서 같은 코드가 동작하도록 구성
  • 분기별 규제 공시 데이터를 코드와 JSON에 하드코딩하던 방식에서 DB 관리로 이관. 테이블 설계와 41개 분기 전수 조사가 필요해 팀에서 선뜻 맡기 어려워하던 건이었지만, 한 번 정리해두면 분기마다 반복되던 작업이 사라진다고 판단해 자원했습니다
  • 이관 과정에서 누적 500여 건의 과거 데이터를 옮기고, 이미 계산되어 공시된 수치는 원본 그대로 저장해 화면에서 재계산하지 않도록 설계. 과거 공시 표기를 그대로 보존하는 것이 정확도보다 우선이라고 봤습니다
Result
  • 1차 개선 범위(전 채널 팝업 일원화, 이미지 직접 삽입, MAU/DAU 조회)를 2026.07 운영 배포 완료
  • 공지와 팝업 등록이 3개 채널 반복 입력에서 1회 등록으로 축소
  • 지표 조회와 이미지 교체가 현업 자체 처리로 전환되어, 개발자 경유 단계가 사라짐
  • 분기 공시 데이터가 DB로 넘어오면서, 매 분기 코드를 수정하고 배포하던 작업이 데이터 등록으로 대체됨
  • 현업으로부터 긍정적인 평가를 받았고, 같은 방식으로 비효율 항목을 계속 발굴해 개선 중
  • 배운 점: 기능을 더하는 것보다 반복을 없애는 방향이 체감 효과가 크고, 개선 대상은 요청서가 아니라 운영 지원 과정에서 발견된다는 것

레거시 API 점진 리팩토링 (Strangler 패턴)

무중단 운영이 전제인 스마트뱅킹 API를, 전면 재작성 없이 기존 인터페이스를 유지한 채 기능 단위로 내부 구현만 교체해 나가는 점진 이관 작업.

Background / Problem
  • 약 2,000줄 규모의 컨트롤러에 채널별 분기와 비즈니스 로직이 함께 들어 있어, 작은 변경에도 영향 범위 파악에 시간이 걸림
  • 금융 채널 특성상 무중단 운영이 전제라 전면 재작성은 리스크가 과도
  • 운영 중 서비스라 자동화된 회귀 테스트에 기댈 수 없어, 변경의 안전성을 별도 절차로 확보해야 하는 조건
Solution / Process
  • URL과 JSON 계약을 동결한 채 내부 구현만 단계적으로 분리하는 Strangler 방식 채택. 유틸과 생성기 같은 순수 로직부터 추출해 위험이 낮은 순서로 진행
  • 이관 전후의 정상 거래 응답을 비교(골든 전문 diff)해 동작 동등성을 확인하고 넘어가는 절차를 먼저 만들고 착수
  • 문제 발생 시 즉시 되돌릴 수 있도록 롤백 경로를 먼저 확보한 뒤 이관 시작
Result
  • 서비스 중단 없이 레거시 영역을 단계적으로 축소하는 중
  • 인터페이스를 유지한 이관이라 프론트와 외부 연동 영향 없이 서버 내부 구조만 개선
  • 비교 검증 절차가 자산으로 남아, 이후 이관도 같은 방식으로 반복 가능
  • 배운 점: 레거시 개선의 성패는 새 코드의 품질보다 롤백 가능성과 검증 절차를 먼저 설계했는가에 달려 있다는 것

위 프로젝트들과 병행해 온 상시 업무. 입사 이후 크고 작은 개발 건 약 230건을 처리했습니다. 다만 요건대로 쳐내는 데 그치지 않고, 반복되는 요청은 그때마다 프로그램으로 바꿔 다음부터는 요청 자체가 발생하지 않게 만드는 방향으로 일해 왔습니다.

주요 대응 유형
  • 서비스 신규 오픈: 안심차단 비대면 신청(2025.10 ~ 2026.03), 금리인하요구권 신청(2025.08 ~ 2025.10) 등 신규 서비스를 화면부터 서버 연동까지 담당

  • 금융 정책, 규제 대응: 상품 구조 변경, 소비자보호 관련 화면, 분기 공시 항목 등 대외 요건 변경에 맞춘 화면과 서버 반영

Deep Dive

기능을 만든 이야기보다, 막혔을 때 어떻게 원인을 좁혔고 무엇을 근거로 방식을 골랐는지가 저를 더 정확히 설명한다고 생각합니다. 그중 두 가지입니다.

Vue 컴포넌트 설계

수정하면 안 되는 컴포넌트를, 수정하지 않고 확장하기

문제
인증서 선택부터 서명, 발급까지 이어지는 흐름을 여러 상품 화면에 붙여야 했습니다. 그런데 기존 인증 모달이 부모 컴포넌트의 특정 메서드를 직접 호출하는 구조여서, 화면마다 같은 코드를 복사해야 했고 성공과 취소가 같은 경로로 들어와 구분조차 되지 않았습니다.
제약
그 모달은 이미 운영에서 검증된 코드였습니다. 금융 화면에서 회귀 위험을 감수하며 원본을 고치는 선택은 하고 싶지 않았습니다.
해결
모달을 자식으로 감싸는 오케스트레이터 래퍼를 만들어, 부모 계약 구현을 래퍼 한 곳으로 모았습니다. 바깥에는 열기 호출과 성공, 취소, 실패 이벤트만 노출해 상품 화면이 모달의 존재를 몰라도 되도록 의존성을 역전시켰고, 중복 콜백 방어 같은 공통 로직도 래퍼에 집약했습니다.
결과
상품별 복사 코드가 사라졌고, 외부 명세나 서명 포맷이 바뀌어도 한 파일만 고치면 전 상품에 반영됩니다. 새 상품 추가는 메타 한 줄과 핸들러 등록으로 끝납니다. 기존 모달은 한 줄도 수정하지 않았습니다.

배운 점. 고칠 수 없는 코드는 감싸서 의존을 뒤집으면 된다. 원본을 건드리지 않고 확장하는 쪽이, 잘 짜인 리팩터링보다 안전할 때가 있다.

WebView 네이티브 브리지

첫 진입에서만 재현되는 버그, 새로고침하면 정상

문제
캐시를 지우고 앱에 처음 들어가면 일부 화면의 조회가 실패했습니다. 그런데 새로고침하면 정상이었습니다. 첫 진입에서만 재현되는 패턴이었습니다.
원인
네이티브가 로그인 세션값을 저장소에 쓰는 시점과, Vue 컴포넌트의 mounted가 실행되는 시점 사이의 레이스 컨디션이었습니다. WebView의 JS가 먼저 실행되면 읽는 순간 값이 비어 있고, 새로고침 때는 이미 써진 뒤라 정상이었던 것입니다.
해결
두 가지 안을 설계하고 트레이드오프로 골랐습니다. 하나는 필수 키가 들어올 때까지 짧은 간격으로 확인하는 폴링에 최대 대기 타임아웃 가드를 둔 방식으로, 네이티브 수정 없이 즉시 적용할 수 있었습니다. 다른 하나는 네이티브가 세팅 완료를 알려주는 브리지 콜백으로, 정확하지만 양측 협의가 필요했습니다. 사용자 영향을 먼저 막는 게 우선이라 폴링으로 배포하고, 이후 네이티브 팀과 협의해 콜백으로 전환하는 단계를 밟았습니다.
결과
첫 진입 실패 제거. 급한 불을 끄는 방식과 옳은 방식을 대립시키지 않고, 순서를 나눠 둘 다 취했습니다.

배운 점. 컴포넌트가 마운트된 시점은 데이터가 준비된 시점이 아니다. 외부에 의존해 무언가를 기다릴 때는 반드시 타임아웃 가드를 둔다.

Result

SBOM 기반 사내 오픈소스 취약점 관리 플랫폼

업무 외 사내 학습 모임(CoP)에서 팀장을 맡아 진행하는 사이드 프로젝트. 사내 오픈소스 자산을 SBOM으로 가시화하고, 취약점을 조기에 탐지해 Slack과 이메일로 알리는 플랫폼의 프론트엔드를 단독으로 맡고 있습니다. React와 TypeScript로 상태 관리와 서버 상태 동기화, 컴포넌트 구조까지 직접 설계하며 제품 수준으로 다루고 있습니다.

Background / Problem
  • 사내에서 쓰는 오픈소스 의존성의 취약점을 수작업으로 추적하기 어렵고, 자산 현황을 한눈에 볼 수단이 없음
  • 취약점 공개 시점과 사내 인지 시점의 간극으로 대응이 지연되는 문제
Solution / Process
  • SBOM(SPDX, CycloneDX) 기반으로 오픈소스 구성요소를 수집하고 자산 현황을 대시보드로 가시화
  • OSV, GitHub Advisory 등 취약점 DB와 매칭하고 AI로 영향도를 분석해 조기 탐지, Slack과 이메일로 자동 알림
  • 팀장으로서 브랜치 전략과 커밋, PR 규칙, 마일스톤을 정하고 코드 리뷰를 운영. TypeScript와 Next.js 프론트엔드는 단독으로 설계하고 구현
Result
  • SBOM으로 사내 오픈소스 자산과 취약점 현황을 한눈에 파악하는 가시성 확보
  • 조기 탐지와 자동 알림으로 취약점 대응 리드타임 단축
  • 협업 규칙과 개발 프로세스를 정립하고 프론트엔드 구조를 담당
  • 배운 점: 도메인 복잡도가 높은 문제도 표준(SBOM)과 자동화를 결합하면 운영 가능한 형태가 된다는 것
